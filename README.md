# dsh-plugin-shop-accounts · 账号管理

> DSH 插件，用于集中管理电商卖家后台的登录态。**一个店铺对应一份独立的登录档案**（ego lite 的 profile，或 Chrome 的 user-data-dir），登录一次后可长期复用，上架脚本直接复用该档案，无需重新登录。
>
> **自 v0.7.0 起支持 ego lite 后端**：检测到 ego lite 时优先使用（每店一个 TaskSpace，同一份「用户配置」可由不同平台的店铺共用）；未安装时回退至 Chrome（每店一份档案与一个固定调试端口）。浏览器后端可在设置页指定，详见[更新说明](#更新说明v0610--v0194)。
>
> **自 v0.10.0 起支持 macOS**：密码改用**系统钥匙串**加密（Windows 使用 DPAPI），浏览器从 `/Applications` 探测，在文件夹中显示时调用 Finder。全部平台相关代码集中于 `lib/platform/`，业务代码不再判断操作系统。

覆盖平台：**拼多多 / 淘宝 / 天猫 / 抖音（抖店）/ 京东（京麦）/ 1688**，均为**商家端**（卖家后台）；同时支持为上述平台的 **C 端买家账号**建档（买家账号仅用于浏览与数据采集，不参与上架）。

## 更新说明（v0.6.10 → v0.19.4）

### v0.19.2–v0.19.4：窗口在别处关掉后状态会不会跟上

窗口是用户在外面关掉的（在 ego 里关掉任务空间，或者直接在任务栏里结束浏览器进程），插件这边并不知道。上一版只有在「等待登录」或「定时任务开着」时才会重新取状态，其余时候安静待着，于是详情页一直停在「浏览器运行中 / 关闭浏览器」。这一版：面板可见时定时对一次状态（请求带 `?fresh=1`，服务端据此绕过 ego 空间列表的 30 秒缓存、强制重列一次），有账号在运行时 2 秒一次、一个都没运行时 10 秒一次；切回窗口 / 标签页重新可见时也立刻对一次；后端发现 ego 主程序不在时直接按「未运行」返回。

### v0.19.1：撤回买家账号的「公开商品监控」

这一版撤回上一版发布又撤下的买家账号采集入口，买家账号回到「只建档、只做登录检测、不做采集」。原因：抖音 / 拼多多的公开商品页在电脑浏览器里没有可用入口（`/mall`、`/shop`、`/product/…` 都是 404，App 分享页只提示「打开抖音 APP」），要抓只能走安卓 App；淘宝 / 天猫 / 1688 / 京东虽然是 PC 页，但需要各自后台的买家账号去登录，当前账号结构下没有实际使用场景。

### v0.18.11：买家账号不做数据采集

| 场景 | 之前 | 现在 |
| --- | --- | --- |
| 买家账号的详情页 | 也显示「数据采集」卡片与采集域（抖店买家能看到抖店那 5 个域） | 买家账号不做数据采集，这一块不再显示 |
| 给买家账号配采集域 | 能存下来，定时任务到点去跑，然后失败 | 采集接口直接拒绝（`COLLECTION_UNSUPPORTED_BUYER`），并提示改用卖家账号 |
| 定时任务 | 买家账号也会尝试采集 | 买家账号只做静默登录检测，采集清单里也不列它 |
| 卖家改成买家 | 原来的采集域还留着，照样到点跑 | 改成买家时一并清空 |

采集读的是商家后台的报表页面（千牛 / 抖店后台 / 京麦 / mms），C 端买家没有这些页面 —— 所以买家账号不做数据采集。

### v0.17.7：定时采集不再漏掉「下载型」配方

抖音、京东这类平台的采集配方，产物是浏览器下载的文件（Excel）。插件自 v0.14.0 起已能把下载文件落盘，但**定时采集**在挑配方时排除了「需要下载」的配方：

| 调用方式 | 挑配方 | 结果 |
|---|---|---|
| 手动指定配方 | 按 id 直接取 | 正常执行 |
| 定时任务（按平台全取） | 过滤掉带下载的配方 | 这些平台「没有可跑的配方」→ 只做登录态检测 |

修复后定时任务按平台取配方时包含下载型；淘宝、拼多多的配方产物是页面文本，行为不变。

验证：新增 9 项自检，其中 2 项用真实店铺跑定时任务路径——抖店一次跑完两份配方（成交分析、收支分析），两份 Excel 全部落盘，采集回写为「成功 2 / 空数据 0 / 失败 0」。

### v0.17.6：站点配方里的非标准选择器与真实鼠标点击

抖音的两份采集配方在真实店铺上跑不通（第 1 步就等元素超时）。原因不在登录态，而在页面选择器：

| 配方里的写法 | 原生浏览器能做什么 | 现在的处理 |
|---|---|---|
| `[role="tablist"]:visible` | 不支持 `:visible` | 用真实可见性（尺寸 + 计算样式）判断 |
| `:text-is("近30天")` | 不支持扩展伪类 | 拆成文字过滤 |
| `.x:has-text("近7天")` | 不支持 | 同上，按文字匹配 |
| `:has(:text-is(...))` | 不支持 | 拆不出 CSS 时退化为「按可见文字找元素」 |
| `//*[normalize-space(.)="近30天"]` | 配方里的 `$` 前缀只是精确文字标记 | 求值前清掉 `$` |

配套变化：

- 点击改成真实鼠标事件（先取坐标，再发 mouseMoved / mousePressed / mouseReleased）；站点的页签组件只认真实输入事件，合成 click 不会改变选中态；
- 执行器里的条件断言先求值再比较（此前在装饰分支里引用了未定义变量）；
- 取不到可用后端时不静默：仍按原路径回退并如实报错。

验证：真机跑通了抖音「成交分析」与「收支分析」两份配方；新增 8 项自检覆盖选择器解析与真实点击。
### v0.17.5：代填点「登录」不再只有一条路径

| 情况 | 站点做法 | 现在的处理 |
|---|---|---|
| 按钮当时不可点 | 等输入校验 / 防抖 / 协议勾选后才放开 | 先让密码框失焦，再点按钮 |
| 提交控件不是按钮 | 用 div / a 当「登录」 | 按可见文字（登录 / 立即登录 / 马上登录 / 提交）找可点元素 |
| 只认表单提交 | 只在 form 的 submit 事件里提交 | 调表单的 requestSubmit() |
| 选择器失效 | 站点改版换了类名 | 依次回退到按文字、表单提交、回车 |

每次代填会记录最终使用的是哪一种方式（`submittedBy`）以及按钮当时是否禁用（`submitDisabled`），
失败时可据此判断是「没点上」还是「点上但没登上」。

### v0.16.7：定时采集在真实店铺跑通（四处修复）

在真实店铺上跑一次定时采集时暴露出四处问题，均已修复：

- **条件守卫不再打断整条配方**：配方用「元素是否出现」判断登录态，而该元素位于跨域 iframe 内（本引擎看不到）。此前这种情况被当作致命错误，整条配方直接失败；现在只记为「条件不成立」，后续步骤照常执行。
- **缺后处理能力会明确报错**：部分平台的采集响应是加密壳，需要专用解密器才能还原成业务数据。此前会把它当成「站点没有数据」；现在在开始采集前就明确报「需要额外能力、本插件暂不支持」，并写进店铺的最近一次采集说明。
- **趋势类接口按单日锚点查询**：这类接口（如生意参谋趋势）要求 `dateRange=当天|当天` 才返回最近 30 天曲线，传整段 30 天区间会被判参数错误。现在查询用锚点日、覆盖台账仍按 30 天记；区间类配方仍用整段范围。
- **采集产物按配方声明归集**：此前后端把产物列表写死为空数组，采到数据也会被判「业务无数据」。现在按配方声明的产物键收集，有值即有数据。
- 另外：`prepareJob` 在「一条都没准备好」且不是「已采过」时返回失败并带上错误码，不再让上层误判为「今天已采过」。

验证：新增 `test/features-v0167.mjs`（13 项）——条件守卫不致命（含两份执行器注入的一致性）、缺能力编译期拒绝、单日锚点与区间口径、产物归集、定时采集把失败原因写到店铺。全套 **15 套自检 403 项**通过。

### v0.15.2：登录凭证错误的识别与暂停

站点将「账号或密码不正确」渲染为一行红色提示文字（HTTP 状态仍为 200），若仅依据 cookie 判定，会将此情况误报为「需要人工处理」；此外逐店串行执行缺少超时机制，单个店铺阻塞会导致整轮任务无法完成。

- 识别中英文错误提示（账号或密码不正确 / 密码错误 / incorrect password 等），并与验证码情况分开分类。
- 密码错误时明确返回 `AUTOLOGIN_BAD_CREDENTIALS`，将该店铺标记为「已暂停自动代填」（附带时间），详情页顶部显示橙色警示卡片说明原因与处理方式，避免连续错误导致账号被锁定。
- 每店采集任务增加超时（默认 15 分钟），单个店铺阻塞不影响后续店铺。

### v0.15.1：登录态失效时自动代填

定时采集遇到 `LOGIN_REQUIRED` 时，使用本机加密保存的密码代填一次；成功后**仅重新执行失败的那几份采集配方**，清除「待登录」标记，并在采集备注中注明「已自动代填后重采 N 份」。遇验证码或短信验证时标记为待登录；未保存密码时提示补录；密码错误时进入 v0.15.2 的暂停逻辑。

### v0.15.0：定时任务调整为定时采集

定时任务的主要用途为定时采集：每店一条任务，到点执行一次采集（而非仅检测登录态）。

- 排期新增 `mode` 字段：`collect`（默认，到点执行采集）/ `check`（仅检测登录态）。
- 到点执行逻辑：已配置采集的店铺走作业编排（prepare → 执行 → advance），并回写 `lastRun*`；未配置采集的店铺退回静默检测。
- **登录态失效时自动代填**（v0.15.1）：使用本机加密保存的密码代填一次，仅重新执行失败的配方；遇验证码或短信验证时标记为待登录；未保存密码时提示补录。无可执行配方时返回 `NO_DSL_FOR_PLATFORM`。
- 设置页新增「到点执行的动作」选择器；`PUT /schedule` 接受 `mode` 字段。

- **作业编排 `lib/collect-runner.mjs`**：`prepare`（分批，每批 ≤5）→ 调用方执行 → `advance`（失败仅重试一次、空数据不重试、无回执保留 pending、revision 防重复提交）→ 生成交付清单；作业状态落盘至 `jobs/<jobId>/job.json`。
- 路由：`POST /accounts/:id/collect-job`（可选 `drive:true` 由插件自行执行完毕）、`.../collect-job/:jobId/advance`、
  `GET .../collect-job/:jobId`、`GET .../collect-jobs`；工具动作 `collect-job` / `collect-advance` / `collect-status` / `collect-jobs`。

### v0.13.0：声明式采集 DSL 引擎

采集配方以**数据**形式描述，而非代码：一份 DSL（JSON 步骤集合）描述「进入哪个页面、点击哪个元素、读取哪个元素、获取哪个产物」。

- 新模块 `lib/rpa.mjs`：DSL 编译（时间窗口、占位符、参数校验）、哑执行器，以及 Chrome / ego 两种 driver。
  登录守卫采用「`when` 命中登录框 → 断言其必须不可见（必然失败）」的方式短路返回 `LOGIN_REQUIRED`。
- 新模块 `lib/dsls.mjs` 与 `lib/rpa/dsls/`：内置 3 份种子配方；`SHOP_ACCOUNTS_DSL_DIR` 可指向任意外部配方库。
- `GET /rpa/dsls` 列出配方；`POST /accounts/:id/collect-run {dslId}` 执行一份配方，返回原始产物与逐步 trace。
- 该版本引擎仅支持读取类流程；**依赖浏览器下载落盘的配方在本版本明确返回 501**，不伪造成功（v0.14.0 补齐）。

### v0.12.0：内置「平台 → 采集域 → 指标」目录层

内置一份「平台 → 采集域 → 指标」骨架，使采集范围有明确定义：

- `lib/catalog/catalog.json`（593 KB，**3045 条指标**）：仅保留「指标 id、名称、所属域、度量类型、时间粒度、写入数据库所需字段」，取值路径、聚合口径、DSL 等实现细节**一律不收录**（有测试断言保障）。
- `lib/catalog.mjs`：按平台查询采集域与指标。**淘宝与天猫为 6 个采集域**（多出「竞争洞察」，78 项指标），抖店、京东、拼多多各 5 个；
  1688 目录中无定时采集子树，退回默认 5 个采集域。
- 校验随目录生效：拼多多选择「竞争洞察」将被 400 拒绝；`collect-import` 中携带的 `metricId` 必须属于该平台目录，
  写入数据库后可按 `metricId` 过滤查询；跨平台 id 直接拒绝。
- `GET /catalog`（工具动作 `action=catalog`）：查询指定平台或采集域的可采指标清单（淘宝运营推广 540 条，默认截断 200 条，`all=1` 返回全部）。
- 界面：采集域按钮显示「域（说明 · N 项指标）」，并提示该平台目录规模。
- **采集能力仍由 skill 或 agent 提供**：目录是目标清单，未接入采集器的指标无法采集。

### v0.9.0 – v0.11.0：密码库 / 账密登录 / 买家账号 / 数据采集 / macOS 适配 / 配置迁移 / 采集数据层

该版本区间补齐账号管理的核心能力：

- **密码库（v0.9.0）**：`<数据目录>/account-secrets.enc`，复用 cookie 罐的主密钥与 AES-256-GCM。
  密码**不写入 `accounts.json`、不进入 `/state`、不进入日志**，账号记录仅保存「已保存状态与更新时间」。
  无可用密钥后端的平台（例如未适配的 Linux）**整库禁用，不得退化为明文**。
- **账密登录（v0.9.2 起）**：新建店铺时「登录账号」与「登录密码」均为**必填**；
  点击「打开店铺」即使用已保存的账号密码代填并提交，无需单独点击「自动登录」按钮。
  代填结果会明确返回（成功、需要验证码、未找到输入框），验证码与短信验证仍需人工完成。
- **卖家 / 买家账号（v0.9.0）**：`accountType` 取值为 `seller` 或 `buyer`，买家账号有独立登录入口；
  能力位区分「能否上架」「能否填写店铺 URL」「能否采集」——买家账号不参与上架。
- **数据采集（v0.9.0）**：仅提供**配置与调度**（选择业务域；执行时间由定时任务排期统一决定，范围固定为最近 30 个完整自然日），
  实际抓取交由 agent 或 skill 完成——平台改版时仅需修改 skill，无需修改插件。
- **采集数据层（v0.11.0）**：将「采集范围」落实为带契约的管线：
  `plan`（该店铺该区间缺少哪些日期）→ skill 采集 → `import`（逐条校验、按 content_hash 去重、记录覆盖台账）→ `query`（查询已采数据）。
  数据存放于 `<数据目录>/collection/<账号id>/`（`coverage.json` 台账、`records.jsonl` 记录、`imports.json` 批次日志）。
  **合法空结果同样记录台账**（仅记录覆盖、不写记录），否则同一区间会被重复采集。对应工具动作：
  `collect-plan` / `collect-import` / `collect-query`。
- **macOS 适配（v0.10.0）**：新增 `lib/platform/`。Windows 使用 DPAPI、Program Files 探测与 PowerShell 进程匹配；
  macOS 使用**钥匙串**（`/usr/bin/security`）、`/Applications` 下的 `.app`、`ps` 解析与 `open`。
  ⚠️ macOS 分支**尚未在真机验证**，验收清单见 CHANGELOG v0.10.0。
- **登录账号查重（v0.10.1）**：同平台且同登录账号（经大小写、前后空格、Unicode 归一化后比较）视为同一账号，
  新建与编辑均会被拒绝（`ACCOUNT_LOGIN_NAME_DUPLICATE`）；跨平台同名正常允许。
  重复记录会导致「代填使用哪个密码、采集结果归属哪个账号」无法对应。
- **店铺配置导出与导入（v0.10.1）**：设置页「路径与高级选项 → 店铺配置迁移」，导出的 JSON 包含
  平台、店铺名、登录账号、店铺 URL 与采集设置，更换机器（尤其 Windows → macOS）时无需逐条重新填写。
  **仅迁移配置，不迁移机密信息**：密码、登录态、档案路径、端口均不包含在导出包中（密码与本机密钥绑定，迁移后也无法解密）；
  导入时逐条校验，无效数据跳过并说明原因，重复条目自动跳过（重复导入不会产生重复记录）。

### v0.7.0 – v0.8.5：新增 ego lite 浏览器后端

本版本区间的主要变更为新增 ego lite 浏览器后端支持。未安装 ego lite 时，插件行为与 v0.6.10 保持一致，
继续使用 Chrome / CDP 后端。

- **账号隔离**：每个店铺对应 ego lite 中的一个 profile 与一个 TaskSpace。profile 为登录态隔离单位，
  TaskSpace 仅承载窗口；登录态保存在 ego lite 的 `User Data` 目录中，与用户在 ego 界面内建立的会话一致。
  上架脚本可通过接口字段 `egoProfile` 复用同一 profile，空间名可选。
- **后端选择**：设置页提供 `自动` / `ego lite` / `Chrome` 三种模式，默认 `自动`（检测到 ego lite 时优先使用）。
  状态胶囊显示当前生效后端与可用 profile 数量；Chrome 模式下不渲染 ego 相关字段。
- **后台检测**：ego lite 未运行时，检测以同一 `User Data` 目录启动无窗口实例（`--headless=new`），
  经 CDP `Network.getAllCookies` 读取 cookie 后立即关闭。实测耗时：淘宝 1697–2086 ms，拼多多 1627 ms；
  检测结束后无残留进程与窗口。ego lite 运行中时，改为在同一 profile 下创建临时 TaskSpace 读取，
  读取完成后销毁，不影响用户当前窗口。
- **进程控制**：所有 ego CLI 调用前先检测主进程状态；仅「打开店铺」「重扫」「启动 ego」允许启动进程，
  其余操作在未运行时直接返回状态。由此避免了状态轮询触发的浏览器启动与历史标签页恢复。
- **控制权交还**：每次操作完成后调用 `handOff()`（失败重试 3 次），TaskSpace 控制权归还用户；
  关联上架插件在会话结束时同样交还。
- **profile 分配**：新建店铺时自动分配未被占用的 profile（优先非默认项）。ego 的 SDK 不支持新建 profile，
  可用 profile 耗尽时返回明确错误。
- **冲突处理**：ego 模式下店铺名即 TaskSpace 名，重名创建返回 400；重置登录态时按平台域名逐条删除 cookie，
  不再清空整个 cookie 库。
- **定时检测**：修复「已点完成」的店铺因 TaskSpace 存在而被持续跳过的问题（v0.8.0）；
  ego lite 未运行时不再跳过检测（v0.8.2）。
- **检测结果处理**：检测失败（进程未运行、CLI 超时、无窗口实例启动失败）时仅记录 `lastCheckError`，
  不覆盖上一次检测结论。
- **已知限制**：
  - ego lite 的 cookie 采用 Chromium 127+ App-Bound 加密，复制档案后无法解密（实测读取 0 个 cookie），
    因此仅支持复用原始档案；
  - 同一 `User Data` 目录同时仅允许一个实例（SingletonLock），插件已对相关调用做串行化处理。

### v0.8.3 – v0.8.4：安全加固

- 移除 CDP 的 `--remote-allow-origins=*` 参数（该参数会使任意网页在 DNS rebinding 之后读取全部登录态）；
- 递归删除、浏览器进程终止、端口归属判定与 cookie 读写，均限制为「该账号自身的档案与端口」；
- HTTP 接口增加访问控制：请求须携带自定义头，拒绝跨站请求，写操作须使用 `application/json`，
  `Host` 须为 IP 字面量或 localhost（用于防御 DNS rebinding）；
- 会话 cookie 备份改为加密存储（Windows DPAPI 保护主密钥 + AES-256-GCM）；
- 自更新仅部署经校验的上游 commit：工作区存在未提交改动时拒绝，无法取得版本号时拒绝，
  `git` 调用禁用 `ext::` 传输并覆盖 hooks 相关配置；
- 拼多多登录态判定收紧：须命中至少 2 个身份 cookie，且必须包含 `PASS_ID` 或 `SUB_PASS_ID`。

各项变更的原因与实测证据见 [CHANGELOG.md](CHANGELOG.md)。

## 功能概览

| 能力 | 说明 |
| --- | --- |
| 一店一档案 | 每个店铺使用独立档案，cookie 互不共享。ego 模式为一店一个 **profile** 与一个 **TaskSpace**；Chrome 模式为一店一个 `user-data-dir` 与一个 CDP 端口 |
| 浏览器后端可选 | **auto**（默认，安装 ego lite 时使用 ego）/ **egolite**（仅用 ego）/ **chrome**（仅用 Chrome）。优先 ego 的原因是它面向「人工与 Agent 共用」设计，登录态与窗口均由其管理 |
| 真实窗口登录 | 启动**有头**浏览器，扫码、密码、滑块等操作由用户在窗口中完成；插件在后台轮询，判定为已登录后点击「完成」，登录态保存至档案 |
| 静默检测 | 在不干扰用户的情况下探测登录态并写回。Chrome 后端使用无头实例（约 2.6–3.1 秒/店）；ego 后端在店铺自身的 TaskSpace 中读取 cookie（该空间会短暂打开） |
| 定时任务 | 每天按排期将全部店铺依次排队执行，状态自动刷新；默认执行定时采集，可配置为仅检测登录态 |
| 保活 | 判定为已登录后让页面多停留数秒再复查，使会话保持活跃（站点访问本身即会续期凭证） |
| 版本与更新 | 在面板中检测 GitHub 新提交，执行快进合并并覆盖安装副本 |
| 多店铺管理 | 支持搜索、按平台筛选、详情页、单店暂停、拖拽排序排期 |

本插件仅负责**维护登录态**：不操作商品、不提交、不改价。

## 安装

**前置条件**：DSH Desktop；本机安装 **ego lite**（推荐，安装后自动优先使用）或 Chrome（未安装 Chrome 时改用 Edge）。

### A. 从源码目录安装（开发场景推荐）

```powershell
dsh plugin --profile <profile名> add file:D:\path\to\dsh-plugin-shop-accounts
```

### B. 手动安装（GUI 中无安装入口时）

1. 将整个目录复制到 `%DSH_HOME%\profiles\<profile名>\node_modules\dsh-plugin-shop-accounts\`；
2. 修改 `%DSH_HOME%\profiles\<profile名>\package.json` 两处：
   - `dsh.profile.bundles` 数组中加入 `"dsh-plugin-shop-accounts"`；
   - `dependencies` 中加入 `"dsh-plugin-shop-accounts": "file:<本目录绝对路径>"`；
3. **重启 DSH Desktop**。

> `%DSH_HOME%` 默认为 `~/.dsh`。
> 插件在**启动时挂载**：修改宿主端代码（`lib/index.js` 等）必须重启；仅修改客户端代码（`lib/client.js`）
> 刷新页面即可生效——但两种修改都必须先将文件同步至 profile 的 `node_modules` 副本。

安装完成后，「设置」中将出现 **账号管理**。

## 快速开始

1. **设置 → 账号管理 → + 新增店铺**：选择平台，填写店铺名（备注可选；Chrome 模式下端口留空表示自动分配）。
2. 点击 **创建并去登录** → 弹出真实浏览器窗口（ego 模式下为该店铺自身的 **TaskSpace**）。
3. 在窗口中登录至**卖家端**后台（各平台入口见[平台表](#支持的平台)）。
4. 返回 DSH，行内状态将自动变为「已登录」→ 点击该行的 **完成并保存**（**ego 模式仅保存状态，该 TaskSpace 保持打开**——
   空间为独立窗口，不影响正常使用浏览器；Chrome 模式则关闭窗口。登录态均已写入档案，如需关闭空间可点击「关闭」）。
5. 此后该店铺持续显示登录态：行内提供供上架脚本使用的两项信息——
   **ego 模式**为「profile 与空间名」，**Chrome 模式**为「调试端口与复制路径」。
6. （可选）点击 **调整排期**，开启定时任务，由插件每天自动执行。

> ego 模式下的 profile 分配：插件会**自动为每个店铺分配一个未被占用的 profile**（优先非默认项）；
> profile 用尽时会返回明确错误，需先在 ego 中新建一个「用户配置」——ego 的 SDK 只能列出与使用已有 profile，不能新建。
> 允许两家店铺共用同一 profile（拼多多与抖音互不冲突），但**cookie 域重叠的平台（淘宝、天猫、1688）必须分开**。

### 浏览器设置

- **浏览器后端**：`自动`（默认，安装 ego lite 时使用 ego）/ `只用 ego lite` / `只用 Chrome`。

- **Chrome 可执行文件**：留空表示自动查找 Chrome，未找到时使用 Edge。
- **启动 ego**（仅在 ego 未运行时出现）：仅启动 ego 主程序，**不操作任何 TaskSpace**。
- **刷新 ego**：重新读取 ego 的 profile 与 TaskSpace 列表（ego 未运行时无法读取，将直接提示「未运行」）。
- **路径与高级选项**（默认收起，v0.8.5 重排）：分为三组——
  **路径**（ego-browser CLI、Chrome、Edge、档案根目录）、
  **Chrome 回退**（起始端口、打开时同时打开商品列表页、关闭时先让浏览器自行退出）、
  **信息**（ego profile、数据目录）。低频配置项集中于此处，设置页默认仅显示「后端与生效状态」。
- 以及 **版本与更新** 卡片。

> **插件不会为读取状态而启动 ego。** 此前每次调用 ego CLI，即使 ego 处于关闭状态，
> 也会将其连同上次的多个标签页一并恢复（实测 5.7 秒、3 GB 内存）——现在所有 CLI 调用前均先检测 ego 主进程状态：
> 未运行则如实返回 `running:false`，仅在用户点击「打开店铺」或「启动 ego」时才会启动。

## 定时任务（排期）

列表上方的横幅即为排期：到点对店铺执行一次**静默检测**（Chrome 后端启动无头实例、不弹窗；ego 后端在店铺自身空间中以只读方式读取 cookie），
结果写回后列表中的「登录状态」随之刷新。点击 **调整排期** 设置：

| 字段 | 说明 |
| --- | --- |
| 每日起始时间 | 每日开始执行的时间 |
| 组间隔（分钟） | 组与组之间的间隔 |
| 每组店铺数 | 每组执行几个店铺；**留空表示自动**（内存 ≤16GB 为 1，>16GB 为 2） |
| 保活停留（秒） | 判定为已登录后多停留数秒再复查，默认 8，0 表示检测完立即关闭 |
| 开启定时任务 | 总开关（关闭时横幅置灰，不执行任何任务） |
| 排期预览 | 显示每个店铺的时间点，**按住 ⠿ 拖动**可调整顺序 |

规则：

- **全部店铺排队**：每 `每组店铺数` 个店铺为一组，同组共用同一时间点，下一组时间为上一组时间加 `组间隔` 分钟。
- **单店开关仅控制「是否执行」**，不影响其占用的时间点——暂停一个店铺不会使后续店铺提前。
- **错过不补执行**：仅在到点后 2 分钟内执行；机器休眠或隔天启动时跳过，不在夜间集中补执行。
- **同一天同一时间点仅执行一次**（记录于 `config.schedule.lastSlots`，重启 DSH 后不会重复）。
- **跳过两类店铺**：等待用户登录的店铺（`pendingLogin`）、Chrome 后端中浏览器已打开的店铺——避免中断用户正在进行的操作。
  ego 后端**不再因「空间已打开」而跳过**（v0.8.0 起）：检测在同一 profile 下**另开一个临时空间**读取 cookie，
  读取完成后立即关闭，全程不接管用户窗口，因此「已点完成的店铺不再检测」的问题已解决。
  临时空间无法读取（ego 未运行）时跳过并记录原因，**不会为执行检测而启动 ego**。
- 宿主每 20 秒检查一次排期；排期开启时界面每 20 秒刷新一次。Chrome 模式下一轮仅启动一个无头实例并串行执行；
  ego 模式在临时空间中读取 cookie（约 2–3 秒，不打开用户窗口）。同一店铺的手动操作与定时任务**共用同一把锁**，
  冲突时定时任务让路（记录为「正在手动操作」），不会出现两个 ego CLI 同时对同一空间执行 takeOver 与 finish。
- 检测失败记录于 `lastSchedError`，行内显示「上次失败」，悬停可查看原因。

### 保活（凭证续期）

判定「已登录」后不会立即关闭浏览器，而是让页面**再停留 `保活停留` 秒**后复查一次——期间页面自身的心跳与 XHR
请求会正常发出，站点将该次访问视为活跃。实测结果（2026-10-19，拼多多真实档案）：

| 时刻 | 读取到的凭证到期时间 |
| --- | --- |
| 11:47:18 该次检测后 | `2027-01-27T03:47:18Z` |
| 18 秒后再次检测 | `2027-01-27T03:47:36Z` |

即**每次访问工作台，站点都会重新下发身份 cookie，并将到期时间重置为访问时刻加 100 天**。
因此续期无需调用刷新接口，定期访问本身即可完成续期。

关于「到期时间」的两条边界说明：

- **到期时间不等于会话可用**：已掉线的店铺 cookie 常仍显示较长有效期（淘宝店铺掉线时 `sgcookie` 仍有一年），
  但服务端会话已失效——登录态判定仍以「站点是否将请求重定向至登录页」为准。
- 保活仅提升会话活跃度，**不保证永不掉线**；掉线时仍如实返回「登录已失效，请重新登录」。

### 关闭窗口后的登录态保持（会话级 cookie）

淘宝卖家登录依赖的 `cookie2` / `_tb_token_` 属于**会话级 cookie**（档案 cookie 库中 `is_persistent=0`），
Chrome 默认关闭窗口即丢弃。这是「登录后点击保存 → 关闭窗口 → 再次打开仍为登录页」的根本原因（v0.6.6 起修复）：

- 启动参数固定包含 `--restore-last-session`：Chrome 才会将会话级 cookie 写入磁盘并在下次启动时读取。
  实测（`shop-accounts-diag/session-cookie-plugin.mjs`，使用插件自身的启动器）：未添加该参数时关闭窗口即丢失；添加后可保留。
- 该参数会同时恢复上次的标签页，因此静默检测改为「自行打开一个干净标签页 → 关闭其他页面目标 →
  仅以该标签页作为判定依据」，避免将恢复出的旧登录页作为判定依据。
- 点击「保存登录态」时，关闭窗口后会**再次复核**：复核未通过则返回 `saved:false` 并说明原因，
  不会再出现「提示保存成功、随即变为未登录」的情况。
- 关闭窗口**之前**还有一道校验：按平台的身份 cookie（淘宝为 `unb` 与 `sgcookie`）逐个核对，
  缺失时每秒重读，最长等待 20 秒；等待 5 秒仍不完整时会主动将窗口导回工作台触发一次；超时后仍不完整则
  **不关闭窗口**、返回 `saved:false` 并说明需等待的时长（v0.6.7）。

  需要等待的原因：2026-10-19 的实测记录显示，工作台已能显示店铺数据时，`unb` 可能尚未写入，
  此时保存并关闭窗口，保存的是一个尚未取得身份的会话。

### cookie 罐本地备份（应对直接关闭窗口）

`--restore-last-session` 仅能覆盖「插件自身关闭窗口」的情况，无法覆盖用户**直接点击窗口关闭按钮**的情况：
2026-10-19 的真机日志中，该次关闭后档案 cookie 从 86 个减少至 42 个，`unb` 直接丢失，下次启动即被重定向至登录页（v0.6.10 起增加保底机制）。

- 只要从浏览器中读到「已登录」，即将整份 cookie 保存至档案目录的 `dsh-session-cookies.json`
  （`<数据目录>/profiles/<账号>/dsh-session-cookies.json`，包含会话级 cookie 的值。**v0.8.3 起加密**：
  AES-256-GCM，主密钥由 Windows DPAPI（CurrentUser）保护——更换 Windows 账号或将文件复制至另一台机器均无法解密）。
- 下次启动浏览器（静默检测、定时任务、点击「打开」）时，先通过 CDP `Network.setCookies` 将**档案中缺失的**
  cookie 补回，再打开页面。仅补充缺失项，不覆盖已有项——档案中已有的同名 cookie 一定比备份更新。
- 该文件会被「清空档案（重扫）」一并删除；如不需要可手动删除，删除后不影响功能（仅失去该层保底机制）。
- 验证：`shop-accounts-diag/cookie-backup.mjs` 8 项全部通过（保存 cookie 罐 → 在页面中使会话级 cookie 过期 →
  补回 cookie 罐 → 会话级 cookie 恢复且页面认可；档案中的新值不会被旧备份覆盖）。

## 登录态判定

1. **登录页最可靠**：站点将请求重定向至登录页即表示站点不认可该会话，即使 cookie 罐中仍保留身份 cookie
   （服务端过期不会清除浏览器 cookie）也判定为未登录。提示文案按「该店铺是否曾经登录」分为两种：
   曾登录 → **登录已失效，请重新登录**；从未登录 → **未登录，请前往登录页登录**。
2. **身份 cookie**：域名匹配且名称命中该平台的身份 cookie，且值不是占位符。匿名 cookie
   （`cna`、`_m_h5_tk`、`sdtoken` 等）所有访客均有，**不计为凭证**。淘宝与天猫要求必须命中 `unb` 或 `sgcookie`
   （空档案停留在千牛登录页时罐中已存在 `cookie2` / `_tb_token_`）；1688 的 `__cn_logon__` 未登录时值为
   `false`，因此校验取值——仅 `=true` 才计为有效。
3. **URL 弱判据**：仅在通过 CDP 读取 cookie 失败时使用，并如实标记为 `evidence: 'url'`（界面中与「确定」区分显示）。

### 静默检测的导航稳定判定

浏览器未打开时，检测会使用无头 Chrome 打开同一份档案探测一次。此场景存在时序问题（v0.3.0 的缺陷，v0.3.1 修复）：

将工作台 URL 作为启动参数传给 Chrome 时，页面目标**立即**停留在工作台 URL（+377ms 即可观察到，CDP 在 +358ms 启动），
而站点重定向至登录页发生在 +632ms。旧实现以「看到平台域名即视为稳定」判定 → 依据的是工作台 URL 与罐中尚未清除的
`PASS_ID` / `SUB_PASS_ID` → **已掉线仍报「已登录」**；窗口打开时可通过实时读取 URL 发现，窗口关闭时则无法发现。

当前 `settlePage()` 仅以「导航真正结束」为判定条件：`document.readyState === 'complete'` 且 URL 连续 1.5 秒不变
（资源持续未结束的站点，URL 稳定 4 秒亦认可；总上限 12 秒），判定依据为稳定后的 URL。
`test/live-probe.mjs` 使用本地页面复现同一时序（先渲染「工作台」，400ms 后由 JS 跳转 `/login`），将该回归固定为测试用例。

## 与上架流程的对接

上架脚本复用某个账号时，需按后端区分：

**ego 模式（推荐）——传入 profile，空间名可选**

- 该店铺的 **profileId**：行内与详情页显示的 `Profile N`，接口字段为 `egoProfile`；
  也可由 Agent 直接查询：`shop_accounts` 工具的 list 输出中包含 `egoProfile` 与 `egoSpace`。
- 上架脚本使用同一 profile 打开其自身的 TaskSpace，**登录态即为有效**（cookie 存储在 profile 级，
  空间仅承载窗口）。拼多多插件的用法：
  ```powershell
  scripts\ego_launch.ps1 -Shop 店铺A -Profile "Profile 3" -Space "店铺-店铺A"
  ```
- 空间名一致时，可在 ego 中看到同一窗口；不传亦可（脚本会自行创建 `pdd-店铺A`），
  只要 profile 正确，登录态仍然有效。

**Chrome 模式——端口与档案路径**

- **调试端口**：行内「调试端口」列显示的值（脚本侧对应 `PDD_PORT` 等环境变量）；
- **浏览器档案**：行内「复制路径」复制的目录（脚本侧对应 `-Profile <档案目录>` 或 `chrome_profile`）。

行内显示 **CDP 可用** 表示该店铺的浏览器正处于打开状态——Chrome 模式下上架脚本应直接连接该端口，**不得再启动新的 Chrome**
（同一份档案被两个实例同时使用会报错，也不符合「复用已登录 profile」的要求）。ego 模式不提供 CDP 端口（ego 不对外暴露），
上架脚本需使用 ego 自身的 SDK。

## 版本与更新

「浏览器设置」中的 **版本与更新** 卡片：

- **当前版本**：当前运行的代码版本号。
- **更新源目录**：本插件的 git 源码仓库（留空表示自动推断：若插件自身位于 git 仓库内则使用自身；否则从 profile 的
  `package.json` 中 `"dsh-plugin-shop-accounts": "file:D:/..."` 反推）。
- **检测更新**：执行 `git fetch` 后比较三项——运行中的版本、源码仓库当前提交的版本、GitHub `origin/main` 的版本，
  落后若干提交也会显示。仅执行查询，不修改文件。
- **更新到最新**：执行 `git merge --ff-only origin/main`（存在未提交改动时拒绝，不代为提交），再将
  `lib/`、`package.json`、`README.md`、`test/` 覆盖至 profile 中的安装副本。
  **仅在检测到确有新版本时才可点击**——未检测、检测失败或已是最新版本时均不可用。

> 覆盖完成后**必须重启 DSH Desktop**：宿主在启动时即将插件代码载入内存，替换文件不会热更新。

安全边界：仅执行 `git -C <更新源目录> fetch/merge` 与本地文件复制，不执行任何远端代码。

## 平台支持（v0.10.0）

Windows 与 macOS 共用一套代码，差异集中于 `lib/platform/`：

| 能力 | Windows | macOS |
| --- | --- | --- |
| 主密钥保护（cookie 与密码） | DPAPI（CurrentUser，经 PowerShell） | **登录钥匙串**（`/usr/bin/security`）；文件中仅保存 `keychain:<service>` 标记 |
| 浏览器可执行文件 | `Program Files` / `LOCALAPPDATA` 下的 `chrome.exe`、`msedge.exe` | `/Applications/<App>.app/Contents/MacOS/<bin>`（Chrome / Edge / Chromium / Brave，也检查 `~/Applications`） |
| 进程按 `--user-data-dir` 精确匹配 | `Get-CimInstance Win32_Process` + 等值比较 | `ps -axo pid=,command=` + 等值比较（`normDir` 归一化） |
| 终止进程树 | `taskkill /PID … /T /F` | `pkill -9 -P` + `kill -9` |
| 「在文件夹中显示」 | `explorer.exe` | `open` |
| ego lite 路径 | 官方安装器的默认位置 | **按 macOS 约定推断，未经真机验证**——找不到时回退至 Chrome 后端 |
| 无密钥后端的平台（Linux 等） | — | —（密码库禁用，不保存明文） |

> ⚠️ **macOS 分支尚未在真机运行**（开发机为 Windows）。验收清单见
> [CHANGELOG v0.10.0](CHANGELOG.md)；可脱离真机验证的部分（路径表、`ps` 解析、钥匙串命名与标记格式、
> 白名单、业务代码中无平台硬编码）均已在 `test/platform.mjs` 中覆盖。

## 已知限制

- **不代为完成登录、不绕过验证码**：扫码、短信与滑块均由用户在真实窗口中完成。
- **ego 的 SDK 不能新建 profile**：只能列出与使用已有 profile。profile 用尽时需先在 ego 中新建一个「用户配置」。
- Chrome 模式：一份 profile 同一时间只能被一个 Chrome 实例占用（插件先探测端口，不会强制启动第二个实例）。
- ego 模式：ego **不对外暴露 CDP 端口**，因此上架脚本不能使用 `connectOverCDP`，只能使用 ego 自身的 SDK（`ego-browser nodejs`）。
- 不支持多账号并发抢占端口：端口按店铺固定分配，冲突时报错而非静默更换端口。
- 仅支持上述六家平台（均为商家端）；上架与发品页面需在具备真实账号登录态后再精确适配，**不推测地址**。
- **ego 的控制权为「借用」**：插件每次操作完成后都会将窗口控制权交还用户（`task.handOff()`，失败重试 3 次），
  因此 ego 中不会长期显示「agent 调试中」；而**检测不需要借用控制权**——它在同一 profile 下另开一个临时空间读取 cookie，
  读取完成后立即关闭，全程不操作用户窗口（v0.8.0 起；旧版本为 takeOver 用户窗口后再归还，会打断用户输入）。
- **ego 关闭时也可执行检测（v0.8.2 起）**：检测时插件会**在后台启动一个无窗口的 ego 实例**（`--headless=new`，
  同一份 User Data、该店铺的 profile），通过 CDP 读取 cookie 后立即关闭——不弹窗、不恢复上次的窗口，
  实测约 1.6–2.1 秒、读取后无残留进程。因此「检测 / 定时检测」无需预先打开 ego。
  但**「打开店铺」仍会启动 ego 主程序**（该操作本身即需打开窗口），启动时 ego 会恢复上次的窗口——这是 ego 自身的行为。
- **ego 模式检测不显示检测窗口**：ego 关闭时使用上述无窗口实例（完全不可见）；ego 运行时在同一 profile 下另开一个临时空间读取 cookie，
  会短暂多出一个空间标签（约 2–3 秒后自动关闭）。
  ⚠️ 存在一个低概率冲突：若**恰好在检测的 1–2 秒内手动打开 ego**，Chrome 的单实例机制可能将该次启动合并至隐藏实例，导致窗口未出现；
  再次点击即可。这是「共用同一份档案」的代价（ego 的 cookie 为 App-Bound 加密，复制档案无法解密，实测 0 个 cookie）。
- **ego 的 profile 不能新建**：SDK 只能列出与使用已有 profile；用尽时会返回明确错误。
- **ego 重启后会话级 cookie 是否保留尚未验证**：Chrome 有 cookie 罐本地备份可应对「直接关闭窗口」，
  ego 没有同类备份（它将登录态保存在 profile 中，正常退出时应当落盘）。此项列为已知限制。
- **重名店铺在 ego 模式下会被拒绝**：店铺名即 TaskSpace 名（`店铺-<名字>`），重名会导致两家店铺共用同一空间、登录态相互混淆。
- 定时任务排期运行于 DSH 宿主进程：DSH 可最小化，但**退出 DSH 后不再执行**。
- 无头检测（Chrome 模式）的 UA 为 `HeadlessChrome`，理论上可能被站点识别（当前六家平台实测正常）；如需规避需单独修改。

## 安全机制（v0.8.3 起，v0.8.4 加强）

以下约束为设计上的硬性要求，修改代码时不得移除：

- **HTTP 接口仅供本插件界面使用**：所有 `/shop-accounts/*` 路由要求自定义头 `x-dsh-shop-accounts: 1`
  （跨站请求携带该头必须先通过 CORS 预检，而本服务从不返回 ACAO），拒绝跨站 `Sec-Fetch-Site`，写请求必须是
  `application/json`；另外要求 `Host` 为 **IP 字面量或 localhost**（防御 DNS rebinding：rebinding 之后
  浏览器发来的 Host 为攻击者域名）。因此「任意网页或局域网页面触发 reset、修改配置、执行更新」的路径不可用。
  （宿主 Desktop 另有 renderer token 门禁，插件不依赖该机制。）
- **调试端口不对网页开放**：启动 Chrome / ego 时**不携带** `--remote-allow-origins=*`。Chrome 仅对携带
  `Origin` 头的 CDP 连接执行 allowlist 校验，而 Node 的 WebSocket 不发送 Origin——不开启该参数同样可读取 cookie，
  开启则等同于允许任意网页在 DNS rebinding 之后读取全部登录态。实测 Chrome 156 可用。
- **递归删除仅识别一种路径形态**：`<档案根目录>/<账号 id>`（`deletableProfileDir()`）。仅判断「位于根目录之下」不足够——
  `profileRoot` 本身可通过设置修改，因此还要求目录名恰为账号 id；**通过导入创建的目录永远不会被插件递归删除**。
  路径判定两侧均使用 `realpath`，junction 与 8.3 短名无法在词法层面绕过。
- **强制终止浏览器按 `--user-data-dir` 精确匹配**：而非「命令行包含该子串」（否则当 profileDir 为
  `C:\Program Files` 时会终止全机浏览器）。
- **端口归属仅认可「自身端口」**：读取与写入 cookie、执行 `Browser.close`、创建 cookie 备份之前均须确认端口属于该店铺
  （运行期登记表 8 小时内且 pid 存活，或进程命令行中的 `--user-data-dir`）；无法确认则不读不写。
  CDP WebSocket 必须为 127.0.0.1 且端口一致。
- **自更新仅部署经校验的 commit**：先无条件执行 `git status --porcelain`（工作区存在改动一律拒绝），再以
  `git archive <上游 commit>` 的内容落地（而非复制工作区），且**必须**取得并匹配版本号（无法取得即拒绝）；
  `git` 调用一律禁用 `ext::` 传输、覆盖 `core.fsmonitor` / `core.sshCommand` / `core.hooksPath`
  （防止通过 `.git/config` 挂载命令）。
- **cookie 落盘加密**：`dsh-session-cookies.json` 使用 AES-256-GCM 加密，主密钥由**系统密钥后端**
  （Windows DPAPI（CurrentUser）/ macOS 钥匙串）保护——更换系统账号或将文件复制至另一台机器均无法解密。文件中仅保留该店铺平台域下的
  cookie，且仅「档案根目录内」的账号有备份（导入目录不写入）。
- **配置中的路径均须通过校验**：`profileRoot` 不得为盘根、家目录、系统或程序目录；`browserPath` / `egoliteCli` /
  `egoliteApp` 必须存在且文件名符合对应程序的命名规则；`updateDir` 必须为绝对路径。
